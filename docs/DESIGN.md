# 設計筆記

這裡放「為什麼這樣做」。都是實際量測或踩坑得到的結論，不是推測——寫下來是為了避免
以後有人（包括我自己）花一輪去重試已經證明行不通的做法。

## 為什麼要有本地歌曲池

`data/pool.json` 把每首歌預先對應到真實的 YouTube videoId。這件事讓查詢時完全不必再打
搜尋 API：選好歌就直接把 videoId 丟進歌單。

代價是要維護這份索引（`collect` + `resolve_pool`），而下面兩節就是維護它時踩到的坑。

## 歌名比對：為什麼需要 pykakasi

pool 的歌名是羅馬字（AnimeThemes 的格式），但 YT Music 目錄以日文為主。早期版本只用
「歌手」當比對條件，結果同一位歌手的不同曲子全部配到同一支影片——實測有 **91 支影片
被 213 首歌共用**。

`ytm/matcher.py` 現在做四件事，每一項都對應一個實際案例：

1. **用 pykakasi 轉羅馬字再比**：「決意の唄」→ `ketsuinota`
2. **標題按「日文名 - 羅馬字名」分段比對**：`Nekohi` 對整串「猫日 - Catdays」只有 0.55，
   對第一段「猫日」是 1.00
3. **歌手名也先羅馬字化**：否則「鈴木このみ」的 token 是空集合，**所有日文歌手名都會被
   閘門擋掉**——這個 bug 讓日文查詢的結果幾乎全被濾光
4. **有日文作品名時多搜一輪「作品名 + OP/ED」**：羅馬字歌名搜不到的曲子常常這樣才撈得到
   （`Hakka`、`Kinnikuman Hero`、`OverThink` 都是這樣救回來的）

還有兩個容易忽略的細節：

- **包含關係要夠長才算數**：`Awa`（3 字）會完美命中 `Shiwaawase`，所以子串長度有下限
- **純符號的歌名**（`○✕△□`、`∞`）轉寫後是空字串，退回比對原字串，否則永遠 0 分、永遠被
  判定為錯配

### 歌名不夠像就放棄，不退回「搜尋第一名」

那個 fallback 正是錯配的來源：YT Music 沒有該曲時，第一名必然是同歌手的別首歌，收下來
只是把錯誤藏起來。代價是官方英譯（「泡」→ Bubbles）也會被放棄——寧可少一首，不要放錯一首。

### LLM 判斷的是語意，不是曲風

實測用消融實驗驗證過：遮掉歌名只留歌手/作品，相關係數 +0.66；遮掉歌手只留歌名，+0.59。
兩個訊號強度差不多，都只是中等相關。而且如果它是靠記憶認曲，紅歌遮掉歌名後判斷應該幾乎
不變——實際上 5600 萬播放的紅歌評分照樣會漂。

**結論：它是從「歌名字面 + 歌手刻板印象」猜的，不是真的認得曲子。** 所以氛圍類需求
（「放鬆的」）的結果可用但不精確。

## 每次 /update 都會重試那些「YTM 找不到」的歌

`resolve_pool` 解不到的歌會從 pool 刪掉，但 `collect` 下次還是會從 AnimeThemes 把它們
抓回來（`save_pool` 的去重是比 `(title, artist)`，而它們已經不在 pool 裡了）。於是每次
`/update` 都會：重新加入 → 花約 1 秒/首去搜 → 還是找不到 → 再刪掉。

實測本季 145 首裡有 27 筆會走這條路，其中約半數是先前確認過找不到的。**結果是正確的
（不會產生重複條目，實測 4215 首、撞號 0），只是白做工約 20 秒。**

刻意不修：加黑名單會讓以後才上架的曲子永遠救不回來，而 YT Music 確實會後補上架。
所以「偶爾重試」算是可接受的浪費。副作用是完成訊息裡的「解不到 N 首（已移除）」
會一直出現同一批名字——那是預期行為，不是 bug。

## cookie：只能由原本登入的瀏覽器續期

`data/browser.json` 幾天到幾週就會失效，而且**沒有純程式的續命辦法**。實測：

| 嘗試 | 結果 |
|---|---|
| 拿掉 `__Secure-1PSIDTS` | library 端點回 0 筆 → **它是必要的** |
| 拿掉 `SIDCC` 家族 | 照常可用 → 不重要 |
| GET `music.youtube.com` | 只回新的 `SIDCC` 家族，**不含 PSIDTS** |
| 帶完整導覽 header（`sec-fetch-*`、`Accept: text/html`）再 GET | 一樣沒有 PSIDTS |
| `accounts.google.com/RotateCookies` | HTTP 500（綁定裝置的 Chrome 專屬機制） |
| 把 cookie 載入另一個瀏覽器（headless Chromium） | 頁面顯示未登入，PSIDTS 沒輪替，**而且整個 session 隨後失效** |

最後一項是關鍵：Google 把「別處複製來的 cookie」視為盜用。**只有當初完成登入的那個瀏覽器
才能替自己續期。** 所以做法是在 NAS 上放一個按需啟動的 Firefox 容器，登入一次之後靠排程
定期開一下讓它自己續，程式端只負責同步。

⚠️ 由此推論：**不要為了測試把 `browser.json` 餵進任何瀏覽器**，那會直接殺掉 session。
要驗證有效性請用 `python -m ytm.cookie --check`。

## 為什麼只有一套認證

先前建歌單走官方 Data API v3 + OAuth，已移除。實測 20 首：

| | Data API v3 | ytmusicapi |
|---|---|---|
| 刪舊 + 開新 | 2.1s | 1.75s |
| 加 20 首 | 20 次呼叫 ≈ **18s** | **1 次呼叫 = 1.73s** |
| 合計 | ~20s | **3.5s** |

原因是 `add_playlist_items` 接受整批 video_id，而 `playlistItems.insert` 一次只能加一首，
**而且對同一歌單的寫入有鎖，無法並行**——並行會回 `409 SERVICE_UNAVAILABLE`，而舊程式只
把失敗計進 `failed`，等於靜默掉歌（實測 8 worker 只成功 1/8）。

所以移除 OAuth 同時達成三件事：少一套認證、少掉 Google Cloud 的設定步驟、建歌單快 5 倍。

代價：cookie 失效時建歌單也會失敗（先前走 OAuth 不受影響）。這讓上一節那套自動續期機制
變得更關鍵。

## LLM 呼叫：關掉 thinking

選曲與挑動作沒有推理步驟可走，reasoning 純粹空轉。實測同一個請求：

```
max_tokens=4000                    10.7s，其中 reasoning 557 tokens，有用輸出 52 字元
加 "thinking":{"type":"disabled"}   1.7s，輸出一樣是合法 JSON
reasoning_effort:"low"             無效，gateway 不吃（照樣 9.9s）
```

而且 reasoning 會把 `max_tokens` 吃光導致 `content` 回空字串，觸發「無 JSON，重試」白跑
一輪——正式環境的 log 裡有 `[agent] 用完 6 步未 final | 總計 163.2s` 這種紀錄。

## 歌單為什麼每次換 URL

重用同一個歌單需要先清空，而清空是 O(N)（逐首移除）；整個刪掉再開新的是 O(1)。
4000 首規模下這個差別很大，代價是歌單 URL 每次都會變。

## 排程為什麼用 host cron 而不是容器

要控制容器就得掛 `/var/run/docker.sock`，那等於給 host root 權限。曾考慮加一個專職的
sidecar 容器來隔離特權，但那讓容器數從 2 變 3，而 host cron + `docker start/stop`
是標準做法且不需要任何額外特權。

已知的脆弱點：DSM 在使用者於「控制台 → 任務排程」增刪任務時會重寫 `/etc/crontab`，
我們加的三行可能被清掉。這是靜默失敗，所以 `firefox-ctl.sh` 每次執行都寫心跳檔，
bot 發現心跳停超過 2 小時會用 Telegram 通知。
